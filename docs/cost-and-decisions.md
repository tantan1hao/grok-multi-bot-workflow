# 成本与专业判断

## 管理者不懂具体技术，怎么判断

把建议拆成可测量的事实、依赖专业知识的解释、需要业务负责人决定的价值取舍。职位高不代表能审核所有细节，另一位 Agent 同意也不等于独立证据。

对“必须换语言”“只能重写”等建议，要求回答：

1. 当前用户问题是什么，证据在哪？
2. 为什么认为原因在这里，排除了哪些其他解释？
3. 保留现状、局部优化和整体变更的收益与代价各是什么？
4. 建议成立需要什么前提，什么证据会让你撤回？

提出者负责主张，独立检查者验证前提和方法，决策负责人处理价值取舍。小团队复用已有角色，避免增加不必要层级。

## 有限试验

```text
争议主张与替代方案：
目前事实 / 推断 / 假设：
输入、环境、测量方法和受检版本：
时间与调用或费用边界，以及边界来源：
可回退方式：
结果满足 X 选 A；满足 Y 选 B：
灰区、停止条件和无结论时的下一步：
```

试验边界只适用这次试验，不自动变成全项目并发或返修上限。已授权、成本相称的验证由负责人推进；改变目标、重要投入或不可逆取舍才交用户决定。

## 怎样控制总成本

| 成本 | 记录与控制 |
| --- | --- |
| 常驻上下文 | 核心短，流程按需加载，只传必要增量与准确指针 |
| 外层与内层调用 | 分开记录通道、请求范围和内部委派 |
| 并行额外开销 | 估计上下文复制、集成、资源争用和减少的等待，按结果调整 |
| 失败和返修 | 记录无效操作与原因，用新证据改变方法 |
| 人工注意力 | 记录用户纠正、催进度和转述次数，只呈现必要决定 |
| 验收 | 按风险选方法，保留有效结果，避免低价值重复检查 |

有实际难度或失败证据时再调整模型或引入专项判断，遵循用户指定工具和额度。环境、权限错误不会仅靠更贵模型解决。

用量按本次请求集合记录；累计值、缓存口径、订阅额度与实际费用分开。未知金额不填零。提示词预算不是硬开关，只有平台提供并验证的限制才可称硬约束。

评价并行看首次合格交付时间和总投入；评价复核看检测能力、漏检和后续结果，不以 Agent 数量、测试数量或发现问题比例单独评分。

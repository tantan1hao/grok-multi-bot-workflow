# 状态与证据

状态回答“到哪一步”，等待原因回答“为什么没继续”，核验时间回答“这句话什么时候查过”。三者分开。

| 状态 | 成立所需证据 | 谁提供 / 复核 |
| --- | --- | --- |
| 待处理 | 原目标、缺口与下一步已记录 | 负责人 |
| 已派发 | 接收方、消息或任务标识、送达记录 | 派发者 |
| 已启动 | 正确原生会话本回合开始，能关联当前任务 | 工程师提供，负责人可核查 |
| 执行中 | 检查窗口内有相关工具结果、编译、调查或阶段产物 | 工程师提供原始来源 |
| 待验收 | 产物版本、要求覆盖、自检与已知限制 | 实现者 |
| 返修 | 失败检查、受影响要求、版本与下一动作明确 | 验收者提出，负责人安排 |
| 已验收 | 检查绑定要求、输入、环境和产物版本 | 中大任务独立验收，小改动可相称自检 |
| 已交付 | 必需检查通过、真实入口走通、约定成果可访问 | 负责人 |
| 已暂停 | 暂停决定，以及执行端停止或等待的实际情况 | 当前控制者与负责人 |

等待原因可为输入、依赖、资源、授权、主机离线、外部故障或无。暂停请求发出但执行仍在运行，要分开说明。

## 到哪里核对

| 对象 | 原始来源 | 单凭什么还不够 |
| --- | --- | --- |
| 原生会话 | 本任务开始、工具动作、结果与终止记录 | 启动器 PID、旧会话存在 |
| 外层 Bot | 实际发送、接收与后续处理记录 | “收到”“我在做” |
| 代码 | 提交号、未提交差异、受检内容与检查结果 | 只有提交号或测试总数 |
| 文档与产物 | 路径、哈希或版本、相关输入与生成时间 | 文件名叫最终版 |
| 成本 | 本次请求集合、时间范围、真实通道和用量来源 | 累计数、未知按零算 |

各入口可观察字段不同，用 [能力表](tool-capabilities.md) 记录。时间从工具取得，不由模型估计。

## 有效范围

脏工作区不能仅用提交号识别，补充受检文件内容版本。文档和配置无需为了验收强行制造提交。

修改要求、输入、环境或产物后，重验受影响部分；无关提交不使全部验收失效。无法证明无影响时保持待复核。

证据目录沿用项目惯例；没有惯例时可用 `artifacts/<任务编号>/`。已有产物建立指针即可，不为凑格式搬迁。

## 新鲜度与接续

按日志、构建阶段、预期首个产物或外部事件约定检查点；无依据的时间估计要标明并随观察调整。超时表示需要复核，不直接表示卡死。

运行信息过期写“上次执行中，核验于……，当前未核实”。历史验收是否仍适用由绑定内容决定。

项目 TODO 为每个入口记录完成怎样被发现：事件、原生轮询或暂无可用方式，附接收者、补查方法、实测日期和证据。同一个会停止的 Bot 再加一句“每天检查”不能证明独立兜底。
